# KRA PIN verification

The administrator opens **Farmers → KRA Verification**. Existing registered farmers appear with a format result calculated from the recorded PIN. Valid format means only that the value matches `^[AP][0-9]{9}[A-Z]$`; it does not establish that KRA issued the PIN or that it belongs to the farmer. Missing and malformed values remain on their original records for correction. The main Admin Farmer Directory displays the recorded PIN after Phone and searches it. The Operations directory does not expose it.

To check a PIN, open the [official KRA iTax PIN Checker](https://itax.kra.go.ke/KRA-Portal/pinChecker.htm) from the workspace, complete its security stamp manually, and compare the returned details with the farmer's registration evidence. Enter the observed outcome, taxpayer name, PIN status, date, verifier, and any remarks or evidence reference. A verified outcome requires the returned name and PIN status. The system derives Exact Match, Possible Match, Mismatch, or Not Checked from the separately stored names. An approximate match calls for review; it is never proof of identity. Each check creates an append-only row with the PIN snapshot, previous and new status, method, actor, and timestamp. Changing the recorded PIN resets the displayed official status to Pending without erasing earlier checks.

New CMS registrations and paper-form imports pass through `createFarmer`, which trims and uppercases PINs. The generated `kra_pin_format` database column recalculates on every insert or edit, including imports. The existing unique PIN constraint rejects duplicates; imports also check for possible duplicates before writing. Scanned PINs and low-confidence transcriptions must be reviewed against the immutable original form. No imported document or transcription is changed by format validation.

Only an authenticated administrator can use `/api/kra-verification` and its history/write endpoints. Ordinary and elevated Operations sessions have no access. At present an accountant performs checks using an Admin account; a scoped accountant login is a separate access-control project and has **not** been granted implicitly. Supporting evidence is stored as a short reference and remarks, not a public upload. Do not include credentials, full tax records, or scanned identity documents in remarks. Verification history is private and has no application role permission to update or delete rows.

## Official API status

KRA's [public PIN Checker](https://itax.kra.go.ke/KRA-Portal/pinChecker.htm) confirms whether a PIN is genuine and uses a security stamp. [GavaConnect](https://www.developer.go.ke/about) advertises developer sign-up and APIs. As of 12 October 2026, publicly accessible material did **not** establish an approved PIN Checker API contract, exact returned fields, authentication method, per-app rate limits, sandbox behavior, or production approval for this use. A GavaConnect article describes sandbox capabilities generally, not this specific API. Accordingly, `officialCheck` in `app/kra-verification.mjs` is an explicit disabled adapter that returns an unavailable error. It must remain disabled until Satima has approved credentials, endpoint documentation, privacy terms, rate limits, and test access. Never automate the public security stamp, scrape the checker, or infer an official result from PIN format.

Before activating a future adapter, confirm the API terms with KRA/GavaConnect, document which taxpayer fields may be stored and for how long, put credentials in private Render environment variables, add server-side request timeouts/rate limiting, and test failure responses. An API failure must leave the PIN pending or unavailable, never verified.

## Deployment and recovery

Migration `016_kra_verification.sql` adds one generated format field and an append-only history table; it does not alter existing PINs or IDs. Take and verify an encrypted backup before applying it. Run `app/scripts/test-hosted.mjs` against its disposable PostgreSQL instance, then apply hosted migrations through `app/scripts/migrate-hosted.mjs` using the existing private owner credentials. Deploy the matching app commit to Render and verify the route, authenticated dashboard, administrator write, and Operations denial using synthetic records only. Recovery retains prior rows by restoring the verified encrypted database backup into an isolated database first; do not overwrite production directly.
